# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Inventory module for a hypothetical hardware store ("Ferretería El Buen Clavo"), a university Software Engineering project. Requirements live **outside this repo** in `../inventario-especificaciones/` (user stories HU-01..HU-34 in `user-stories/User-Stories.pdf`, a story map with releases R1/R2/R3, and C4 architecture diagrams). Code comments reference story ids (`# HU-09: ...`); keep doing that when implementing a story.

The user writes in Spanish. UI text and DB column names are Spanish; code comments are English.

## Commands

Frontend (`frontend/inventory-display/`, Angular 22, served on http://localhost:4200):
```bash
npx ng serve            # dev server
npx ng build            # build; use this to check templates/types compile
npx ng test --watch=false   # unit tests (Vitest + jsdom via @angular/build:unit-test)
npx ng test --watch=false --include src/app/core/services/auth-service.spec.ts   # single spec
```
Formatting is Prettier (`printWidth: 100`, single quotes, Angular parser for HTML), configured in `.prettierrc`.

Backend (`backend/`, Flask on http://localhost:5000, run from `backend/`):
```bash
.venv/bin/pip install -r requirements.txt   # only direct dependencies, written by hand (not pip freeze)
.venv/bin/python main.py      # debug=True, auto-reloads
```
Docker (from the repo root; see "Docker and deploy" below):
```bash
cp .env.example .env          # once; .env is gitignored
docker compose up --build     # db + backend + frontend, open http://localhost:4200
docker compose logs -f backend
docker compose down           # stop (data kept)   ·   down -v also deletes the DB volume
```

There is no backend test suite. Endpoints are checked ad hoc with `create_app().test_client()` (log in via `POST /api/v1/login` to get a token) or curl. The user usually has their own Flask already running on port 5000, so prefer `test_client` over starting or killing a server. Always delete test rows you insert into the database.


## Architecture

### Backend (Flask + MariaDB)
- `app/__init__.py` `create_app()` loads `.env` (located at `backend/app/.env`: `FLASK_KEY`, `DB_*`, `JWT_SECRET`, `JWT_EXPIRES_IN` in hours), enables CORS for `http://localhost:4200` only, and registers one blueprint per feature folder (`auth`, `catalog`, `suppliers`, `movements`, `users`, `counts`, `sales`) with `url_prefix='/'`. Routes declare the full path themselves: `@bp.route('api/v1/<name>')`. Empty folders (`alerts`, `units`, `inventory-service`) are placeholders for future features.
- `suppliers/suppliers.py` (HU-09): `GET api/v1/suppliers` (all, active and inactive), `GET api/v1/suppliers/<id>`, and admin-only `POST api/v1/add-supplier`, `PUT api/v1/edit-supplier/<id>` and `PUT api/v1/supplier-status/<id>` (`{activo: bool}`, deactivate or reactivate). Add and edit share `_read_supplier()` for validation; on edit, `supplier_nit_exists(nit, exclude_id)` lets a supplier keep its own NIT. `add-entry` rejects an inactive supplier (400).
- HU-10 (owner only), in `suppliers.py`: `GET api/v1/suppliers/<id>/products` (`proveedor`, `resumen` {productos, facturas, ultima_compra} and `productos`, newest purchase first) and `GET api/v1/products/<id>/suppliers` (cheapest last price first, `mas_barato` on the cheapest when there are 2+). Both come from `AccessData.PURCHASES_QUERY`: a CTE over `entrada` movements of **valid** invoices (voided ones do not count) with `ROW_NUMBER() OVER (PARTITION BY producto, proveedor ORDER BY fecha_factura DESC, entry id DESC)`, joined to itself for the previous purchase (n = 2). Each row (`_purchase_to_json`): `precio` per base unit, `precio_presentacion` as on the invoice, `fecha_factura`/`numero_factura`/`entrada_id` of the last invoice, `precio_anterior`, `fecha_anterior`, `cambio` (%), `veces` (lines bought) and `total` (base unit). Decided 2026-11-17: owner only, invoice date (not the registration date).
- HU-23 (owner only), in `suppliers.py`: `GET api/v1/purchase-order`. `AccessData.get_purchase_order()` takes the low-stock products (same rule as HU-22, CTE `bajos`) and, per product, its **last valid invoice from any supplier** (CTE `ultima`, `ROW_NUMBER() OVER (PARTITION BY producto ORDER BY fecha_factura DESC, entry id DESC)`; voided invoices do not count) with the supplier (`contacto`, `telefono`, `activo`), the price per base unit and the presentation it came in. Flask groups by `proveedor_id` (`None` = never bought by invoice, "Sin proveedor", last). `_suggested_order` (decided 2026-11-19, option A): order enough to end at **2 × mínimo** (`2·min − existencia`), rounded UP to whole presentations of the last invoice (60 lb with 50 lb cajas → 2 cajas = 100 lb) or to a whole base unit; at least 1 (a mínimo of 0 would give 0). Each line (`_order_line_to_json`): `sugerido` (base unit), `presentacion` {nombre, factor, cantidad} or null, `precio` (last invoice, else `products.precio_compra`, else null), `precio_presentacion`, `costo`, `ultima_compra`. Response: `fecha`, `proveedores` [{proveedor_id, nombre, contacto, telefono, activo, productos, total, sin_precio}], `resumen` {productos, proveedores, total}.
- `movements/movements.py` holds the invoice entries (HU-11/HU-12): `POST api/v1/add-entry`, `GET api/v1/entries` (`?faltantes=true` for only those with shortages) and `GET api/v1/entries/<id>`. The client sends quantities and price **per presentation, as printed on the invoice**; Flask converts them to the base unit before saving (2 cajas at Q400 → 100 lb at Q8/lb), and responses carry both forms (`cantidad`/`precio` in base unit, `*_presentacion` as on the invoice). All lines are validated before anything is written, and `AccessData.add_entry` saves the header and its movements in one transaction.
- HU-14 (owner only), in `movements.py`: `PUT api/v1/void-entry/<id>` (`{motivo}`) and `PUT api/v1/correct-entry/<id>` (`{motivo, ...same body as add-entry}`, answers 201 with the **new** entry). Nothing is deleted: `AccessData._void_lines` inserts one `anulacion` movement per `entrada` line (same cantidad, precio, presentation, supplier, `entrada_id` and the motivo), marks the entry with `anulada_en`/`anulada_por`/`motivo_anulacion` and calls `_restore_purchase_price` (puts back the price of the last valid invoice, only if no later valid invoice and no manual `compra` change in `price_history` came after the voided line). `correct_entry` voids and then calls `_insert_entry` (shared with `add_entry`) in **one transaction**, so the stock check uses the net result (95 − 100 + 10 = 5). `_check_stock_change(cursor, {producto_id: delta})` locks with `_lock_stock`, in id order, every product that loses stock and raises `NegativeStock`; the routes answer **409** with `data.productos` (`codigo, nombre, unidad_base, existencia, quedaria`). Already voided → 400 `entry is already voided` (also raised as `EntryAlreadyVoided` inside the transaction, where the entry row is locked `FOR UPDATE`). `add-entry` and `correct-entry` share `_read_entry(access, body, original)`; a correction may keep the original's supplier and products even if they were deactivated since, and `entry_exists(proveedor_id, numero, exclude_id)` only counts valid entries. `GET entries` and `GET entries/<id>` return `anulada`, `anulada_en`, `anulada_por` (name), `anulada_por_id` and `motivo_anulacion`; they only count/list the `entrada` rows, and `?faltantes=true` leaves voided entries out.
- `movements.py` also holds outputs (stock that leaves without a sale): `POST api/v1/add-output` (`{tipo, producto_id, cantidad, motivo}`, any logged-in user) and `GET api/v1/outputs` (latest 100, newest first). `OUTPUT_TYPES` is `("dano", "uso")` (HU-16 merma, HU-17 uso interno); `GET outputs?tipo=dano|uso` filters. `cantidad` is always in the base unit (no presentations) and `motivo` is required (≤200). `precio` is the product's **purchase price per base unit** (`products.precio_compra`, read by `_last_purchase_price()` inside the same transaction; NULL if it was never bought) so reports can tell how much was lost or used; responses also carry `costo` = cantidad × precio. HU-18: `AccessData.add_output` calls `_lock_stock(cursor, producto_id)`, which does `SELECT ... FOR UPDATE` on the product row and recomputes the stock inside the same transaction, then raises `InsufficientStock(existencia)` if it does not reach. The route answers **409** with `data: {existencia}` and Angular writes "Solo hay N en existencia". Reuse `_lock_stock` for every outgoing movement (uso interno, future sales) so two people cannot take the same last units.
- HU-20 kárdex, in `movements.py` (owner only): `GET api/v1/product-movements/<id>?desde=&hasta=&page=&per_page=` (dates `YYYY-MM-DD`, `hasta` includes that whole day; `per_page` 25/50/100). `AccessData.get_product_history` computes `existencia` (stock right after each movement) with `SUM(...) OVER (ORDER BY fecha, id)` over **all** the product's movements and only then filters by date and paginates (`LIMIT/OFFSET`), so it is right on any page or range. Response: `producto` (with current `existencia`), `resumen` (`inicio`, `entro`, `salio`, `final` of the whole range, not the page), `movimientos` (newest first; `cantidad` signed, `costo`, supplier/invoice, `anulada` only on voided `entrada` rows, presentation as on the invoice), `total`, `page`, `pages`, `per_page`. A voided entry and its `anulacion` both count in entró/salió.
- HU-31 (owner only), in `catalog/initial_load.py` (routes on the `catalog` blueprint, imported from `catalog/__init__.py`; uses `openpyxl`): `GET api/v1/initial-load/template` (an .xlsx with a `Productos` sheet: Código, Nombre, Categoría, Unidad, Precio venta, Precio compra, Mínimo, Existencia, with drop-downs for unidad and the active categories from a hidden `Listas` sheet, plus an `Instrucciones` sheet), `POST api/v1/initial-load/preview` and `POST api/v1/initial-load` (multipart field `archivo`, .xlsx ≤2 MB, ≤1000 rows, titles matched ignoring case/accents, empty rows skipped). Both check every row and answer `{filas: [{fila, codigo, accion: nuevo|existente, ..., errores: [Spanish messages]}], resumen: {filas, nuevos, existentes, con_error, valor}}`; the save answers 400 with that data if any row has an error and saves **nothing** (decided 2026-11-17: fix the Excel and upload again). A new codigo creates the product; an existing one without movements only gets its stock and (optional) purchase price, the rest of the row is ignored; an existing one with movements is an error (use a physical count). With existencia > 0 the purchase price is required. `AccessData.initial_load` saves all in one transaction, locks the existing products and raises `ProductHasMovements` (→ 409 `data.codigos`) if one got a movement meanwhile; a codigo taken meanwhile → 409. Each stock is one `inicial` movement (`precio` = precio_compra, motivo "Carga inicial desde Excel"). `read_new_product(raw)` in `catalog.py` is the shared check for a new product (returns fields and a list of Spanish errors) used by both `add-product` (first error as the 400 message) and the Excel load; `read_initial_stock` checks existencia. `add-product` also takes optional `precio_compra` and `existencia` (HU-31 by hand: an `inicial` movement with motivo NULL), and now rejects a sale price with more than 2 decimals.
- HU-27 (owner only), in `movements.py`: `GET api/v1/movements?desde=&hasta=&tipo=&usuario_id=&page=&per_page=` (same date/page rules as the kárdex; `tipo` from `AccessData.MOVEMENT_TYPES`). Returns `movimientos` (newest first, same row shape as the kárdex via `_history_row_to_json` plus `producto_id`, `codigo`, `producto`, `unidad_base`; no `existencia`), `por_tipo` ({tipo, movimientos, dinero = SUM(cantidad × precio)}; quantities are not added because units mix) which ignores the tipo filter, `por_usuario` ({usuario_id, usuario, movimientos}) which ignores the user filter, and `total/page/pages/per_page`. `AccessData._movement_filters(..., skip=)` builds the WHERE.
- `catalog.py` also has `GET api/v1/low-stock` (HU-22, any logged-in user): active products with a `stock_minimo` whose stock is at or below it, out of stock first, then by `existencia / stock_minimo` ascending (percent, so lb/m/units are comparable); each row carries `faltan` and `agotado`. The stock is computed in a subquery because MariaDB cannot sort by an expression on a SUM alias.
- HU-26 (owner only), in `catalog.py`: `GET api/v1/inventory-value`. `AccessData.get_stock_with_cost()` returns every product with stock > 0 (inactive ones too: the merchandise is still there) with `precio_compra`; Flask computes `valor` = existencia × precio_compra and returns `total`, `productos_con_existencia`, `por_categoria` (`productos`, `valor`, `porcentaje`, `sin_precio`; most valuable first), `productos` (most valuable first) and `sin_precio`. Products without `precio_compra` are left out of the totals and listed instead of counted as Q0. On 2026-11-16 the 7 products that had NULL `precio_compra` (all without movements) were set to 70 % of their sale price directly in the DB.
- Categories (HU-05), in `catalog.py`: `GET api/v1/categories` (any logged-in user; all of them with `activo` and `productos` = how many products use it) and admin-only `POST api/v1/add-category`, `PUT api/v1/edit-category/<id>` (rename) and `PUT api/v1/category-status/<id>` (`{activo}`). Names are trimmed with spaces collapsed, ≤50, unique ignoring case (409). `categoria_id` is **required** on add/edit product and must be an active category; `_check_category(access, id, keep_id)` lets an edited product keep its current category even if it was deactivated.
- HU-04 (owner only), in `catalog.py`: `PUT api/v1/product-status/<id>` (`{activo}`; 404/400; data `{id, activo}`), via `AccessData.set_product_active`. Soft delete only: movements stay, so the kárdex and reports keep the product. Decided 2026-11-20 (option A): a product **with stock** can be deactivated (the `confirm()` warns how much is left); that stock still counts in HU-26 and counts, but it cannot be sold or taken out until reactivated. Searches, entries, outputs, sales, Existencias, low-stock and the purchase order already left inactive products out.
- Product editing (HU-21 mínimo + HU-02 precios, both `admin` only): `GET api/v1/products/<id>` returns the product with `precio_compra`, `presentaciones`, `tiene_movimientos` and `historial_precios`; `PUT api/v1/edit-product/<id>` takes `{codigo, nombre, categoria_id, unidad_base, stock_minimo, precio, precio_compra}`. Rules: codigo unique excluding itself (409); `precio` ≤2 decimals, `precio_compra` ≤4 decimals and it cannot be emptied once set; `unidad_base` cannot change if the product has movements, nor become `unidad` if a presentation has a decimal factor; `stock_minimo` whole for `unidad`. `AccessData.update_product` locks the row, updates it and inserts one `price_history` row per price that actually changed, in one transaction. Presentations and `activo` are not edited here. The plain product list (`GET api/v1/products`) deliberately does not return `precio_compra` (money is owner-only, HU-29).
- `users/users.py` (HU-30, all `admin` only): `GET api/v1/users` (never returns `password_hash`; the PK is aliased `users AS id`), `POST api/v1/add-user` (`{nombre, email, rol, password}`; email lowercased, duplicate → 409), `PUT api/v1/user-password/<id>` and `PUT api/v1/user-status/<id>` (`{activo}`; the owner cannot deactivate themselves → 400). **The role is permanent**: it is chosen on creation and there is deliberately no route to change it. New passwords need at least 6 characters (`PASSWORD_MIN` in Flask and in `add-user.ts`); `AccessData.hash_password()` is the single place that hashes.
- `counts/counts.py` (HU-32/33/34 physical count, all done): `GET api/v1/counts/current` (the open count or `data: null`), `GET api/v1/counts/<id>` (with `items` and `categorias`; **never the system stock**, HU-32), `POST api/v1/add-count` (`{categoria_ids}`, any logged-in user; 409 if one is already open) and admin-only `PUT api/v1/cancel-count/<id>`. HU-33: `PUT api/v1/count-items/<id>` (`{items: [{producto_id, contado}]}`, one sheet, any logged-in user; `contado` null = not counted, ≥0, ≤3 decimals, whole for `unidad`; 400 if the count is not open or a product is not in it) and admin-only `GET api/v1/counts/<id>/compare` (items with `existencia` now, `precio_compra`, `diferencia` = contado − existencia, `dinero` = diferencia × precio_compra, plus `resumen`: contados, pendientes, con_diferencia, faltante, sobrante, neto, sin_precio). `AccessData.save_count_items` locks the count row (`CountNotOpen`) and only writes rows whose value changed (`NOT (contado <=> ...)`), so re-saving a sheet keeps who counted it. HU-34 (admin only): `GET api/v1/counts` (latest 50, every estado; `Count` carries `ajustes` = movements with that `conteo_id`) and `PUT api/v1/apply-count/<id>` (`{ajustes: [{producto_id, motivo, detalle, diferencia}]}`): `motivo` from `ADJUSTMENT_REASONS`, `Otro` needs `detalle` (≤150) and is saved as `"Otro: <detalle>"`; only counted products, `diferencia` ≠ 0, no repeats. Only the listed products are adjusted (partial apply) and the count **always closes** as `aplicado`; an empty list closes it with no adjustments (everything matched). `AccessData.apply_count` locks the count, then each product in id order (`_lock_stock`), recomputes `contado − existencia` and raises `CountChanged` if any differs from the `diferencia` the owner saw → **409** with `data.productos` (`existencia, contado, diferencia, aprobada`) and nothing applied. Each adjustment is one `ajuste_mas`/`ajuste_menos` movement (`cantidad` = abs, `precio` = `precio_compra` of the moment, `motivo`, `conteo_id`), so the stock ends equal to what was counted and never negative. `compare` adds `ajuste` per item (`tipo`, signed `cantidad`, `motivo`, `dinero`) from `get_count_adjustments`; the kárdex rows carry `conteo_id`. `AccessData.add_count` puts in the active products of those categories plus inactive ones that still have stock, and raises `CountAlreadyOpen` from the `uq_counts_abierto` IntegrityError. Decided 2026-11-16: compare against the stock **at the moment** (no snapshot; the adjustment will be `contado − existencia actual`), one open count at a time, anyone starts/prints/enters counts, only the owner sees stock/money and applies (partial apply allowed), one motivo per adjusted product chosen from Pérdida / Error de registro / Producto dañado / Producto encontrado / Otro.
- `sales/sales.py` (HU-15, built 2026-11-19 because the billing module will not be made; any logged-in user): `POST api/v1/add-sale` (`{nit_cliente, nombre_cliente, items: [{producto_id, cantidad}]}`, 201 with the sale), `GET api/v1/sales?fecha=YYYY-MM-DD` (that day, default today, newest first; `{fecha, ventas, total}`) and `GET api/v1/sales/<id>` (with `items`: codigo, nombre, unidad_base, cantidad, precio, subtotal). `cantidad` in the base unit (no presentations), > 0, ≤3 decimals, whole for `unidad` (HU-07); products must exist and be active, no repeats, ≤50 lines. `normalize_nit()`: "CF"/"C/F"/empty → `CF`, otherwise digits + check digit (0-9 or K) with SAT's **modulo 11** (weights 2, 3, 4… from the right, `(11 − sum % 11) % 11`, 10 = K), saved as `1234567-9`; with a NIT the nombre is required, with CF it defaults to "Consumidor Final" (≤100). The price is **`products.precio` (sale price) at that moment**, never sent by the client (HU-02/HU-29). `AccessData.add_sale` runs in one transaction: `_check_stock_change(cursor, {id: -cantidad})` locks every product in id order (HU-18) and raises `NegativeStock` → **409** `data.productos` (codigo, nombre, unidad_base, existencia), nothing saved; then reads the prices, inserts the `sales` header (total = Σ round(cantidad × precio, 2)) and one `venta` movement per product with `venta_id`. Responses carry `iva` = total − total/1.12 (Guatemala, prices include 12 % IVA). No voiding of sales (decided 2026-11-19, option A): a wrong sale will be fixed with HU-13 (devolución) when it is built. The kárdex/HU-27 rows carry `venta_id`.
- HU-13 (any logged-in user), in `sales.py`: `POST api/v1/add-return` (`{venta_id, motivo, items: [{producto_id, cantidad, danado}]}`, 201 with `devolver` = money to give back and the updated `venta`) and `GET api/v1/returns` (latest 50 returned lines, with `danado`). Decided 2026-11-20: **always against a ticket** (the sale number; the frontend also lets the user pick the sale from a day's list when the paper is lost), **no time limit**, a damaged one = `devolucion` + `dano` of the same quantity (option A), and HU-24 subtracts returns. Only products of that sale, `cantidad` > 0, ≤3 decimals, whole for `unidad`, no repeats, `motivo` optional ≤150. `AccessData.add_return` locks the `sales` row `FOR UPDATE`, recomputes vendido − devuelto per product and raises `ReturnTooMuch` → **409** `data.productos` (`vendido, devuelto, por_devolver`); then one `devolucion` row per line (`precio` = the sale price of that ticket, `motivo`, `venta_id`) and, if `danado`, a `dano` row (precio_compra, motivo `"Devolución dañada (venta #N): <motivo>"`, same `venta_id` and the same `fecha`, which is how `get_returns` tells it was damaged). `GET sales/<id>` items carry `devuelto` and `por_devolver`, and every sale carries `devuelto` (money); `SALE_SELECT` counts `productos` with `tipo = 'venta'` only because return rows also have `venta_id`. `get_top_sales` nets returns (`cantidad`/`dinero` = venta − devolucion in the range, `devuelto` per product, `HAVING ventas > 0`) and its `resumen` has `vendido` (tickets), `devuelto` (`get_returned_money`) and `dinero` = the difference; the dashboard chart (`por_dia`) stays the tickets' total.
- HU-24 (owner only), in `sales.py`: `GET api/v1/top-sales?desde=&hasta=` (both optional, `hasta` includes that day). `AccessData.get_top_sales` sums only `venta` movements per product (most sold quantity first, decided 2026-11-20 option A; inactive products included) with `cantidad`, `ventas` (distinct tickets), `dinero` and the current `existencia`; Flask adds `bajo_minimo` (HU-22 rule). `get_sales_by_day` groups the `sales` headers by day. Response: `desde`, `hasta`, `resumen` {productos, ventas, dinero}, `productos`, `por_dia` [{fecha, ventas, total}] with **every** day of the range filled with 0 when both dates are given and the range is < 366 days (otherwise only the days with sales).
- HU-25 (owner only), in `sales.py`: `GET api/v1/stale-products?dias=30|60|90` (default 90, else 400). `AccessData.get_stale_products(desde)`: products (inactive too) with stock > 0, no `venta` since `desde` (or never) **and** first movement before `desde`, so what arrived recently is not counted (decided 2026-11-20, option A). Each row: `existencia`, `precio_compra`, `dinero` (existencia × precio_compra, null without price), `ultima_venta` (YYYY-MM-DD or null), `dias_sin_vender` (since the last sale, or since it arrived when never sold), `nunca_vendido`. Most money first, without price last (option A). `resumen`: productos, dinero, valor_bodega (HU-26 total), porcentaje, nunca_vendidos, sin_precio.
- Dashboard (decided 2026-11-20: employees also see the money in the store and the sales chart), in `sales.py`: `GET api/v1/dashboard-summary?dias=7|30` (any logged-in user; default 30, else 400) returns `dinero_bodega` (HU-26 total, same rule: products without `precio_compra` left out), `desde`, `hasta`, `por_dia` (`_sales_per_day`, shared with `top-sales`), `mas_vendidos` (the first `DASHBOARD_ROWS` = 4 of `get_top_sales` for those days: cantidad, ventas, dinero), `ultimas_ventas` (the 4 latest sales of any day, `_sale_to_json`) and `ultimos_movimientos` (the 4 latest movements of any type from `get_movements(limit=4)`, via `_activity_to_json`: tipo, cantidad, signed `cambio`, producto, usuario, `venta_id`, `numero_factura`; **no price**). The full reports (`inventory-value`, `top-sales`, Análisis) stay owner only; the dashboard calls only this endpoint.
- `app/access_data/access_data.py` `AccessData` is the only place with SQL. Pymysql with `DictCursor`, one connection per method via the `_connection()` context manager, explicit `conn.commit()` on writes. Add new queries as methods here.
- `app/security/require_role.py` `@requiere_rol(*roles)` goes under `@bp.route`. It validates the `Authorization: Bearer` JWT (HS256), reloads the user from the DB and sets `g.user`. Missing/expired/invalid token or an inactive user returns 401; wrong role returns 403. `@requiere_rol()` with no args means any logged-in user. Roles are `admin` (owner) and `employee`; writes to the catalog, suppliers and users are `admin` only, while entries and outputs can be registered by any logged-in user (employees receive the truck and register broken product). The login JWT also carries `nombre` and `rol` (HU-29) so Angular can hide options; they are only for the UI, since `requiere_rol` always reloads the role from the DB.
- Response shape: `{"status": 0|1, "message": ..., "data": ...}` (0 = ok). Login is the exception: it returns `token` at the top level. Validation errors are 400, a duplicate unique value is 409 (check first, and also catch `pymysql.err.IntegrityError`), and creation is 201.
- Decimals and tinyint booleans are converted to `float`/`bool` before returning (see `_product_to_json` in `catalog.py`).
- Optional unique strings (e.g. `suppliers.nit`) must be stored as `NULL` when empty, never `''`, so the UNIQUE constraint allows several blanks.

### Database
`backend/query.sql` holds the schema (C4 level 4 data model) and seed data. Keep it in sync when the schema changes. `backend/inventory_dump.sql` is a full `mariadb-dump` of the `inventory` DB with dummy data (drops and recreates every table); it is a snapshot, not the source of truth for the schema. ### Styling quirks
Tailwind v4 is set up through PostCSS (`src/styles.css`), but `src/index.html` also loads a Tailwind 2.2 CDN stylesheet. Many component templates were copied from a "Cordes" dashboard theme and still contain `<head>`, `<script>` and `<body>` tags. Their `<link>` tags do get added to the page when the component renders, so Font Awesome icons (including the sidebar's) only load on pages whose template has that `<head>` block; a page without it (e.g. `add-user`) loses the icons. The user is handling this. The custom `cordes-*` colors are not reliable either: use plain Tailwind color classes **that exist in Tailwind 2.2** (its default palette is gray, red, yellow, green, blue, indigo, purple, pink; e.g. `amber-*` and `orange-*` render as nothing, use `yellow-*`). Internal links should use `routerLink`, not `href`, to avoid a full page reload.
