# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Inventory module for a hypothetical hardware store ("Ferretería El Buen Clavo"), a university Software Engineering project. Requirements live **outside this repo** in `../inventario-especificaciones/` (user stories HU-01..HU-34 in `user-stories/User-Stories.pdf`, a story map with releases R1/R2/R3, and C4 architecture diagrams). Code comments reference story ids (`# HU-09: ...`); keep doing that when implementing a story.

The user writes in Spanish. UI text and DB column names are Spanish; code comments are English.

## Commands

Frontend (`frontend/inventory-display/`, Angular 22, served on http://localhost:4200):
```bash
npx ng serve            # dev server
npx ng build            # build; use this to check templates/types compile
npx ng test --watch=false   # unit tests (Vitest + jsdom via @angular/build:unit-test)
npx ng test --watch=false --include src/app/core/services/auth-service.spec.ts   # single spec
```
Formatting is Prettier (`printWidth: 100`, single quotes, Angular parser for HTML), configured in `.prettierrc`.

Backend (`backend/`, Flask on http://localhost:5000, run from `backend/`):
```bash
.venv/bin/pip install -r requirements.txt   # only direct dependencies, written by hand (not pip freeze)
.venv/bin/python main.py      # debug=True, auto-reloads
```
There is no backend test suite. Endpoints are checked ad hoc with `create_app().test_client()` (log in via `POST /api/v1/login` to get a token) or curl. The user usually has their own Flask already running on port 5000, so prefer `test_client` over starting or killing a server. Always delete test rows you insert into the database.


## Architecture

### Backend (Flask + MariaDB)
- `app/__init__.py` `create_app()` loads `.env` (located at `backend/app/.env`: `FLASK_KEY`, `DB_*`, `JWT_SECRET`, `JWT_EXPIRES_IN` in hours), enables CORS for `http://localhost:4200` only, and registers one blueprint per feature folder (`auth`, `catalog`, `suppliers`, `movements`, `users`) with `url_prefix='/'`. Routes declare the full path themselves: `@bp.route('api/v1/<name>')`. Empty folders (`alerts`, `units`, `inventory-service`) are placeholders for future features.
- `suppliers/suppliers.py` (HU-09): `GET api/v1/suppliers` (all, active and inactive), `GET api/v1/suppliers/<id>`, and admin-only `POST api/v1/add-supplier`, `PUT api/v1/edit-supplier/<id>` and `PUT api/v1/supplier-status/<id>` (`{activo: bool}`, deactivate or reactivate). Add and edit share `_read_supplier()` for validation; on edit, `supplier_nit_exists(nit, exclude_id)` lets a supplier keep its own NIT. `add-entry` rejects an inactive supplier (400).
- `movements/movements.py` holds the invoice entries (HU-11/HU-12): `POST api/v1/add-entry`, `GET api/v1/entries` (`?faltantes=true` for only those with shortages) and `GET api/v1/entries/<id>`. The client sends quantities and price **per presentation, as printed on the invoice**; Flask converts them to the base unit before saving (2 cajas at Q400 → 100 lb at Q8/lb), and responses carry both forms (`cantidad`/`precio` in base unit, `*_presentacion` as on the invoice). All lines are validated before anything is written, and `AccessData.add_entry` saves the header and its movements in one transaction.
- `movements.py` also holds outputs (stock that leaves without a sale): `POST api/v1/add-output` (`{tipo, producto_id, cantidad, motivo}`, any logged-in user) and `GET api/v1/outputs` (latest 100, newest first). `OUTPUT_TYPES` is `("dano", "uso")` (HU-16 merma, HU-17 uso interno); `GET outputs?tipo=dano|uso` filters. `cantidad` is always in the base unit (no presentations) and `motivo` is required (≤200). `precio` is the product's **purchase price per base unit** (`products.precio_compra`, read by `_last_purchase_price()` inside the same transaction; NULL if it was never bought) so reports can tell how much was lost or used; responses also carry `costo` = cantidad × precio. HU-18: `AccessData.add_output` calls `_lock_stock(cursor, producto_id)`, which does `SELECT ... FOR UPDATE` on the product row and recomputes the stock inside the same transaction, then raises `InsufficientStock(existencia)` if it does not reach. The route answers **409** with `data: {existencia}` and Angular writes "Solo hay N en existencia". Reuse `_lock_stock` for every outgoing movement (uso interno, future sales) so two people cannot take the same last units.
- `catalog.py` also has `GET api/v1/low-stock` (HU-22, any logged-in user): active products with a `stock_minimo` whose stock is at or below it, out of stock first, then by `existencia / stock_minimo` ascending (percent, so lb/m/units are comparable); each row carries `faltan` and `agotado`. The stock is computed in a subquery because MariaDB cannot sort by an expression on a SUM alias.
- Categories (HU-05), in `catalog.py`: `GET api/v1/categories` (any logged-in user; all of them with `activo` and `productos` = how many products use it) and admin-only `POST api/v1/add-category`, `PUT api/v1/edit-category/<id>` (rename) and `PUT api/v1/category-status/<id>` (`{activo}`). Names are trimmed with spaces collapsed, ≤50, unique ignoring case (409). `categoria_id` is **required** on add/edit product and must be an active category; `_check_category(access, id, keep_id)` lets an edited product keep its current category even if it was deactivated. The category filter for the product lists is pending (the user did not want a separate filters component; to be decided).
- Product editing (HU-21 mínimo + HU-02 precios, both `admin` only): `GET api/v1/products/<id>` returns the product with `precio_compra`, `presentaciones`, `tiene_movimientos` and `historial_precios`; `PUT api/v1/edit-product/<id>` takes `{codigo, nombre, categoria_id, unidad_base, stock_minimo, precio, precio_compra}`. Rules: codigo unique excluding itself (409); `precio` ≤2 decimals, `precio_compra` ≤4 decimals and it cannot be emptied once set; `unidad_base` cannot change if the product has movements, nor become `unidad` if a presentation has a decimal factor; `stock_minimo` whole for `unidad`. `AccessData.update_product` locks the row, updates it and inserts one `price_history` row per price that actually changed, in one transaction. Presentations and `activo` are not edited here. The plain product list (`GET api/v1/products`) deliberately does not return `precio_compra` (money is owner-only, HU-29).
- `users/users.py` (HU-30, all `admin` only): `GET api/v1/users` (never returns `password_hash`; the PK is aliased `users AS id`), `POST api/v1/add-user` (`{nombre, email, rol, password}`; email lowercased, duplicate → 409), `PUT api/v1/user-password/<id>` and `PUT api/v1/user-status/<id>` (`{activo}`; the owner cannot deactivate themselves → 400). **The role is permanent**: it is chosen on creation and there is deliberately no route to change it. New passwords need at least 6 characters (`PASSWORD_MIN` in Flask and in `add-user.ts`); `AccessData.hash_password()` is the single place that hashes.
- `app/access_data/access_data.py` `AccessData` is the only place with SQL. Pymysql with `DictCursor`, one connection per method via the `_connection()` context manager, explicit `conn.commit()` on writes. Add new queries as methods here.
- `app/security/require_role.py` `@requiere_rol(*roles)` goes under `@bp.route`. It validates the `Authorization: Bearer` JWT (HS256), reloads the user from the DB and sets `g.user`. Missing/expired/invalid token or an inactive user returns 401; wrong role returns 403. `@requiere_rol()` with no args means any logged-in user. Roles are `admin` (owner) and `employee`; writes to the catalog, suppliers and users are `admin` only, while entries and outputs can be registered by any logged-in user (employees receive the truck and register broken product). The login JWT also carries `nombre` and `rol` (HU-29) so Angular can hide options; they are only for the UI, since `requiere_rol` always reloads the role from the DB.
- Response shape: `{"status": 0|1, "message": ..., "data": ...}` (0 = ok). Login is the exception: it returns `token` at the top level. Validation errors are 400, a duplicate unique value is 409 (check first, and also catch `pymysql.err.IntegrityError`), and creation is 201.
- Decimals and tinyint booleans are converted to `float`/`bool` before returning (see `_product_to_json` in `catalog.py`).
- Optional unique strings (e.g. `suppliers.nit`) must be stored as `NULL` when empty, never `''`, so the UNIQUE constraint allows several blanks.

### Database
`backend/query.sql` holds the schema (C4 level 4 data model) and seed data. Keep it in sync when the schema changes. `backend/inventory_dump.sql` is a full `mariadb-dump` of the `inventory` DB with dummy data (drops and recreates every table); it is a snapshot, not the source of truth for the schema. The DB user lacks CREATE privileges, so the user runs DDL (`ALTER TABLE`, etc.) themselves; provide the query instead of executing it.
- `users` PK column is named `users` (not `id`). Passwords are stored as SHA256 hex. Test users: Don Rigo and José Sosa (`admin`) and Kevin Pinones (`employee`, `kevin.pinones@elclavo.com`) are in the DB; David Jimenes (`employee`) is only in `query.sql`. They use password `12345`, except Kevin, whose password is `123456` (changed from the Usuarios page). There may also be users the user created by hand (e.g. Byron Castañeda); do not change their passwords.
- **Stock is never stored**: existencia = SUM over `movements` (`entrada` adds; `venta`, `dano`, `uso` subtract), always in the product's `unidad_base` (`unidad` integers only; `lb`/`m`/`gal` allow decimals, HU-07).
- `presentations` convert purchase units to base units (1 caja = 50 lb, HU-06). They are created together with the product: `POST api/v1/add-product` takes an optional `presentaciones: [{nombre, factor}]` and `AccessData.add_product` saves product and presentations in one transaction. Rules (checked in `_validate_presentations` in `catalog.py` and again in the Angular form): name required (≤30, case-insensitive unique per product), factor > 0 with at most 3 decimals, and a whole number for `unidad` products. `GET api/v1/presentations` returns all of them and the frontend filters by `producto_id`.
- `entries` is an invoice header (supplier, `numero_factura`, `fecha_factura`, who and when). `UNIQUE(proveedor_id, numero_factura)` prevents entering the same invoice twice (409). Each product of the invoice is one `entrada` row in `movements` with `entrada_id`, `presentacion_id` (NULL = came in the base unit) and `proveedor_id` (kept filled so HU-10 can query by supplier).
- In `movements`, `precio` is per base unit with 4 decimals (Q100 per 30 m roll = Q3.3333/m). For entries, `cantidad` is what actually arrived (must be > 0; a product that did not arrive is not entered) and `cantidad_factura` is what the invoice says (optional in the form, defaults to `cantidad`). An entry "has shortages" (HU-12) when any line has `cantidad_factura <> cantidad`; this is computed in queries, not stored.
- `suppliers` has `nombre` (required), optional `telefono`, `contacto` (seller name) and `nit` (UNIQUE), and `activo`.
- `products.categoria_id` is NOT NULL (HU-05: every product belongs to a category).
- Soft delete via `activo` on `categories` (HU-05: products that have it keep it, but new products cannot pick it and no product can be changed to it), `products` (HU-04: inactive products are hidden from searches), `suppliers` (HU-09: still listed, greyed out, but cannot receive new invoices; old entries keep pointing to them) and `users` (HU-30: inactive users cannot log in).
- Prices (decided 2026-11-13, option "C"): `products.precio` is the **sale** price and `products.precio_compra` (decimal 12,4, NULL = never bought) the **purchase** price, both per base unit. Every invoice (`add_entry`) sets `precio_compra` to that line's price, and the owner can correct it in Editar producto. `price_history` (producto, `tipo` venta|compra, `precio_anterior`, `precio_nuevo`, usuario, fecha) records only the owner's manual changes; invoices are their own record. HU-26 (stock × purchase price) should use `precio_compra`.
- In `movements`, `precio` means: what was paid for `entrada`, and `products.precio_compra` at that moment for `dano`/`uso` (outputs registered before HU-17, e.g. one hammer merma, have NULL and the user chose to leave it).
- `movements.motivo` (varchar 200) is the reason for `dano` and `uso`; a CHECK (`chk_movements_motivo`) makes it required and non-empty for those two types. It is NULL for entries and sales.
- `stock_minimo` NULL means the product generates no low-stock alerts (HU-21).
- Sales (HU-15) are NOT built here: they will come from a separate billing project ("módulo de facturación") through the Flask API. The rest of EP-05 (HU-16 merma, HU-17 uso interno, HU-18 stock validation) is built here, one story at a time, and the HU-18 check must be reusable by a future sales route. What was agreed for that integration (auth, product `codigo`, idempotent invoice number, price owner, cancellations) is in `facturación-conditions.txt` at the repo root; read it before touching sales.
- Known gap: Editar producto does not touch presentations yet, so they cannot be added to an existing product. `add-product` has no purchase-price field (it stays NULL until the first invoice or an edit). The SRC-001 serrucho is wrongly in `m`; the user will fix it later. Outgoing movements are `dano` (HU-16) and `uso` (HU-17); sales wait for the billing module, so EP-05 is done except HU-15.

### Frontend (Angular 22, standalone components, signals)
- `app.routes.ts`: `home` (guarded by `publicGuard`, holds `login`) and `content` (guarded by `authGuard`). `content` renders the `SideBar` plus a `<router-outlet>`; feature pages are its lazy-loaded children (`dashboard`, `settings`, `products`, `products/add-product`, `suppliers`, `suppliers/add-supplier`, `products/edit-product/:id`, `suppliers/edit-supplier/:id`, `users`, `users/add-user`, `categories`, `entries`, `entries-list`, `outputs`); the `add-*`, `edit-*` and `users` routes also have `adminGuard`.
- `core/services/auth-service.ts` keeps the JWT in localStorage and a signal. `isAuthenticated()` decodes the token's `exp` client-side and logs out when it has expired. `email()`, `nombre()`, `rol()` and `isAdmin()` are computed from the token payload (decoded as UTF-8 so accents survive); a token without `rol` (issued before HU-29) counts as `employee`.
- HU-29 (the employee does not see what they cannot use): `core/guards/admin-guard.ts` (`adminGuard`) protects owner-only routes (`products/add-product`, `products/edit-product/:id`, `suppliers/add-supplier`, `suppliers/edit-supplier/:id`, `users`, `users/add-user`; add it to future prices/reports pages) and sends employees to `/content/dashboard`. Owner-only buttons and sidebar links (Usuarios, Análisis) are wrapped in `@if (isAdmin())`; components get it with `isAdmin = inject(AuthService).isAdmin`. The sidebar shows the real name and Dueño/Empleado. Flask's 403 remains the real protection. Employees do enter the invoice (purchase) price when registering an entry; that is intended. "Los precios solo yo" refers to the product's sale price.
- `core/services/auth-interceptor.ts` (functional interceptor registered in `app.config.ts`) adds the Bearer token to every request except login, and on any 401 logs out and redirects to `/home/login`. Components therefore do not handle 401, only 0/403/409 and the like.
- `core/services/data-services.ts` `DataServices` wraps all non-auth API calls and maps `response.data`. Response and entity interfaces live in `models/`, mirroring the Flask JSON.
- Feature components live in `utils/<name>/`. List pages (`products`, `suppliers`) follow the same pattern: `loading`/`error` signals, a `query` signal bound to the search input, and a `filtered` computed that matches every typed word against accent-stripped, lowercased text. Add pages (`add-product`, `add-supplier`) use reactive forms with `invalid(field)`, `saving`/`error`/`created` signals, and an `errorMessage()` that maps HTTP status codes to Spanish messages. `add-product` also has a typed `FormArray` (`presentaciones`, accessed via the `presentations` getter) for the "Se compra en" rows; remember to `clear()` it after a successful save because `form.reset()` does not remove rows. `add-supplier` doubles as the edit page: `editId` comes from the `:id` route param (null = create); in edit mode it loads the supplier with `getSupplier(id)`, sends `editSupplier()` and navigates back to the list. The `suppliers` list shows Estado and, for the owner only, Editar and Desactivar/Reactivar (`toggleActive()`, asks `confirm()` before deactivating). The `entries` supplier select uses `activeSuppliers`.
- `entries` (HU-11/HU-12) has two reactive forms: `form` for the invoice header and `lineForm` for the product being added. `addLine()` validates the line (including HU-07 whole numbers for `unidad` products after applying the presentation factor) and pushes it into a `lines` signal; `save()` sends everything in one `addEntry()` call. The "Viene en" select comes from `unitOptions()`: the product's presentations, biggest first, plus the loose base unit. `entries-list` lists entries with a "Solo con faltantes" filter and expands a row to load its products with `getEntry(id)`. `fecha_factura` is a `YYYY-MM-DD` string formatted by hand, not with `DatePipe` (which would parse it as UTC and can show the previous day).
- `users` (HU-30) lists users with Rol and Estado. "Cambiar contraseña" opens an in-page modal (`passwordFor` signal + `passwordForm`); Desactivar/Reactivar asks `confirm()` and is hidden on the owner's own row (`isMe()`, compared by `AuthService.email()`). `add-user` picks the role with two radio cards and warns that it cannot be changed later. Both password forms ask for the password twice (`passwordsDiffer`).
- `outputs` (HU-16/HU-17, "Sacar Mercadería") has a Daño | Uso interno toggle (`tipo` signal; titles, labels, button text and color come from the `texts` record via `t()`). It picks the product with a search box (HU-03 matching, active products only, max 8 results, Enter picks the first) instead of a select, then shows "Hay N en existencia". `quantityProblem` checks HU-07 and HU-18 while typing; on a 409 from Flask it updates the product's stock with `data.existencia` and shows "Solo hay N en existencia". Below the form it lists the latest outputs with Tipo and Costo columns and a Todos/Daño/Uso interno filter (`filterOptions`, `shownOutputs`). `products` rows have a "Sacar" link (active products with stock) to `/content/outputs?producto=<id>`, which preselects the product.
- `categories` (HU-05, owner only: `adminGuard`, sidebar link inside `@if (isAdmin())`) is one page: a "Nueva categoría" box, the list with Productos and Estado, inline rename (`editingId`/`editName`; Enter saves, Escape cancels) and Desactivar/Reactivar with `confirm()`. `nameProblem()` mirrors Flask's name rules. `add-product` offers only `activeCategories`; `edit-product` offers `categoryOptions` (active ones plus the product's current one, marked "(inactiva)"). Neither has "Sin categoría" anymore.
- `dashboard` (HU-22) is still the Cordes template with fake data, **on purpose**: the user wants it kept and only added two things at the spots they marked with comments. Under the header, a notification ("N productos se están acabando · M sin existencia", red if any is out of stock, yellow otherwise, green "Todo en orden" when none) with an "X"; closing it stores `lowStockDismissed` in `sessionStorage` and it stays closed until logout (`AuthService.logout()` calls `sessionStorage.clear()`). At the end of `<main>`, the "Productos a agotarse" table (Producto, Existencia, Mínimo, Faltan, Estado). Do not remove or redesign the rest of the dashboard unless asked; a full redesign was tried and reverted.
- `edit-product` (HU-21/HU-02) is its own component (not `add-product` in edit mode). It loads `getProduct(id)`, disables `unidad_base` when `tiene_movimientos`, shows a live margin ("Gana Q15.00 por u (16.7 %)" / red "Pierde Q5.00 por u"), asks `confirm()` before saving a sale price below the purchase price (HU-02 "avisa antes de guardar"; a warning, not a block), shows presentations read-only and a "Cambios de precio" table from `historial_precios`. After saving it stays on the page and refills the form. `products` rows have an "Editar" link for the owner.
- Services use Angular 22's `@Service()` decorator.

### Styling quirks
Tailwind v4 is set up through PostCSS (`src/styles.css`), but `src/index.html` also loads a Tailwind 2.2 CDN stylesheet. Many component templates were copied from a "Cordes" dashboard theme and still contain `<head>`, `<script>` and `<body>` tags. Their `<link>` tags do get added to the page when the component renders, so Font Awesome icons (including the sidebar's) only load on pages whose template has that `<head>` block; a page without it (e.g. `add-user`) loses the icons. The user is handling this. The custom `cordes-*` colors are not reliable either: use plain Tailwind color classes **that exist in Tailwind 2.2** (its default palette is gray, red, yellow, green, blue, indigo, purple, pink; e.g. `amber-*` and `orange-*` render as nothing, use `yellow-*`). Internal links should use `routerLink`, not `href`, to avoid a full page reload.
